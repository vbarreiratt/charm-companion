# Touch Navigation: Home ↔ Scenes

**Date:** 2026-09-06
**Status:** Implemented and validated on real hardware, including standalone (no serial monitor attached) — see "Post-implementation: touch reliability bug" below. Native suite 78/78.
**Depends on:** 2026-09-06-hardware-iteration-harness-design.md (harness used to verify this)

## Interaction design (confirmed with user)

- **Home → Scenes:** swipe gesture (finger moves up a threshold distance while touching the screen, on the Home screen). Not a tap on the existing launcher button — the button stays purely visual for now.
- **Scenes → Home:** the physical BOOT button (GPIO 0). Single press: go back one step. From any scene after the first, that means the previous scene. From the first scene, that means exit to Home. Long-press is explicitly out of scope (deferred, to be discussed later).
- Touch inside a scene keeps its existing per-scene meaning (blink the eye, speed up the planet) — swipe/back navigation must not interfere with that.

## Architecture

- **`SwipeDetector`** (`src/shell/swipe_detector.h/.cpp`) — pure logic, no hardware dependency. Fed `(touched, x, y)` once per tick; returns a `SwipeDirection` (`NONE`/`UP`/`DOWN`/`LEFT`/`RIGHT`) the instant a touch-release completes a motion past threshold. Extracted as its own class specifically so it's unit-testable without `TouchHAL`, whose native (non-`ARDUINO`) fallback always reports "not touched" — the same reason `render_reference.cpp` calls `on_touch()` directly instead of going through the real touch driver.
- **`ButtonHAL`** (`src/shell/hal/button_hal.h/.cpp`) — new HAL, same singleton/`init()` pattern as `DisplayHAL`/`TouchHAL`/`IMUHAL`/`PowerHAL`. Wraps `BOOT_BUTTON_PIN` (GPIO 0, active-low, `INPUT_PULLUP`) with debounce and edge detection: `was_pressed()` returns true once per fresh press, not continuously while held. Native fallback always returns false (matches `TouchHAL`'s "nothing happening" default).
- **`App::handle_back()`** — new virtual method on the `App` base class, default returns `false` (nothing to go back to). `ScenesApp` overrides: if not on the first scene, moves to the previous scene and returns `true`; if already on the first scene, returns `false` (nothing left to go back to within Scenes — the caller should exit to Home). This avoids needing RTTI (disabled on this build, `-fno-rtti`) or a name-based `static_cast` hack to let `Shell` special-case `ScenesApp`.
- **`Shell::handle_boot_press()`** — new public method (mirrors `poll_sensors()` being public specifically so tests can call it directly without a real `ButtonHAL` press). Calls `current_app->handle_back()`; if that returns false and the current app isn't already "home", switches to Home.
- **`Shell::poll_sensors()`** — gains: feed `SwipeDetector` from the same touch poll already happening (no behavior change to existing `TOUCH_EVENT` publishing); on `UP` while current app is "home", switch to "scenes". Also polls `ButtonHAL::instance().was_pressed()` and calls `handle_boot_press()` if true.

## Testing strategy

- `SwipeDetector`: fully unit-tested in isolation (no HAL, no Arduino) — feed synthetic `(touched, x, y)` sequences, assert the returned direction.
- `ScenesApp::handle_back()`: unit-tested directly (register test scenes, call repeatedly, assert index decrements then returns false at index 0).
- `Shell::handle_boot_press()`: unit-tested directly via a mock `App` overriding `handle_back()`, without touching `ButtonHAL` — same pattern `ShellIntegrationTest` already uses for `MockTestApp`.
- `ButtonHAL`/native GPIO reading: not unit-tested (no native fallback behavior beyond "always false", same as `TouchHAL`) — validated on real hardware via the `hardware-iterate` loop (serial console log + physical button press).
- End-to-end: native suite green → flash → confirm via serial log (`app home` → swipe simulated via injected touch sequence, or physical swipe → scene changes; boot press → scene goes back / exits to Home).

## Post-implementation: touch reliability bug (found, diagnosed, fixed same day)

Right after building the above, physical touch turned out to work only intermittently — sometimes fine, sometimes silent for 30+ seconds. This took real investigation to run down, in order:

1. **First (wrong) hypothesis:** `TouchHAL` never checked `TOUCH_INT_PIN`, just polled `getPoint()` blindly every tick — unlike `waveshareteam/ESP32-S3-Touch-AMOLED-1.75C`'s reference examples, which gate reads on a `FALLING` interrupt. Tried adding interrupt-gating plus a `sleep()`/`reset()` wake cycle from those examples. This made things *worse* (interrupt never fired; `sleep()` crashed the I2C bus with `ESP_ERR_INVALID_STATE`) — root cause of *that*: the Waveshare GitHub repo vendors a different, incompatible fork of SensorLib than the one actually pinned in this project's `platformio.ini` (`lewisxhe/SensorsLib.git@2b9e591f...`). That pinned version's own bundled example uses plain unconditional polling and explicitly warns `sleep()` breaks touch on this chip. Reverted to unconditional polling (see `src/shell/hal/touch_hal.cpp`'s comments) — this was a real dead end, not a fix, but ruled out an incorrect theory before it caused more damage.
2. **Decisive test:** flashed the board's actual factory firmware (`Firmware/ESP32-S3-Touch-AMOLED-1.75C-FactoryOnly-260114.bin` from the Waveshare repo) directly via `esptool`, on a throwaway `test/factory-firmware-touch-check` branch. Touch worked perfectly. This ruled out a hardware defect and proved the bug was 100% in this project's software.
3. **Found the real reference implementation:** the factory firmware's touch driver (`waveshare/esp32_s3_touch_amoled_1_75c` BSP → `waveshare__esp_lcd_touch_cst9217`) isn't on GitHub, but a cached copy existed locally in a sibling project (`/Users/vitor/Desktop/esp32-badge`'s `managed_components/`, an unrelated ESP-IDF project pulling the same managed component). Its read function retries up to 5 times with delays between the register-address write and the data read, and hardware-resets the chip if every retry fails — SensorLib's `getPoint()` has none of that; a single failed I2C transaction permanently reports "no touch" until something unrelated unsticks it. Rewrote `TouchHAL::get_touch_point()` from scratch against this exact protocol (register `0xD000`, ACK byte `0xAB`, same bit-packed finger data), bypassing SensorLib's read path entirely (its `begin()`/init sequence was kept — chip detection never failed). New pure function `TouchHAL::parse_touch_data()` is unit-tested natively (`tests/test_touch_hal.cpp`). Verified via the hardware-iterate harness: two consecutive 35s continuous-touch windows went from 0-5 log lines (near-total silence) to 253 and 77 lines respectively, zero multi-second gaps.
4. **Still not fully fixed:** touch worked whenever a session was actively watching the serial log, but stopped as soon as the monitor disconnected. Root cause: `HWCDC` (the `Serial` implementation on this USB-CDC-on-boot board) defaults to a 100ms TX timeout with up to 20 retries (~2s total) per `write()` call — every `Serial.print()` blocks for up to ~2 seconds when nobody is reading the USB CDC port and its ring buffer fills up. `Shell::poll_sensors()` prints on every detected touch, so once unplugged, every touch stalled the entire main loop for up to 2s — indistinguishable from "touch stopped working." Fixed with one line, `Serial.setTxTimeoutMs(0)` in `main.cpp`'s `setup()`, making prints non-blocking regardless of whether a host is attached. Confirmed by the user testing standalone, no monitor attached: works.

Both fixes (task 3's protocol rewrite and task 4's non-blocking Serial) are real, independently-verified improvements — not redundant. The retry/reset logic matters when a genuine I2C transaction fails; the TX timeout fix matters regardless of touch chip behavior and would have affected any frequent `Serial.print()` in this codebase, not just touch.
